# HREVN Managed Service

Private VPS-backed runtime for HREVN.

## Current scope
- `GET /v1/health`
- `GET /v1/version`
- `POST /v1/baseline-check`
- `POST /v1/profile/validate`
- `POST /v1/verify-bundle`
- `POST /v1/generate-bundle`
- `GET /v1/bundles/{bundle_id}/download`

The service is intentionally thin:
- auth
- orchestration
- normalized outputs

Canonical HREVN semantics stay in `hrevn-core`.

`verify-bundle` currently accepts a local `source` path so we can validate the
runtime end-to-end before adding upload/download flows for the VPS deployment.

## Authentication

When `HREVN_REQUIRE_API_KEY=true`, authenticated endpoints require:

`Authorization: Bearer <API_KEY>`

Keys are configured through:

`HREVN_API_KEYS=key1:customer:plan:license_id,key2:customer:plan:license_id`

Current public endpoints:
- `GET /v1/health`
- `GET /v1/version`

Current authenticated endpoints:
- `POST /v1/baseline-check`
- `POST /v1/profile/validate`
- `POST /v1/verify-bundle`
- `POST /v1/generate-bundle`
- `GET /v1/bundles/{bundle_id}/download`

## Verified Record V1

The current stable product baseline is the minimum HREVN bundle:

- `payload.json`
- `issuance.json`
- `manifest.json`
- `CHECKSUMS.sha256`
- `ROOT_HASH_SHA256.txt`

This minimum profile is the canonical `Verified Record` / `Registro Verificable`
layer used to package outputs generated by other HREVN services.

Current characteristics:
- reproducible ZIP generation
- SHA-256 checksums for every artifact in the bundle
- root hash over the authoritative files declared in `manifest.json`
- compatibility with the legacy verifier plugin

Expected default verifier warnings for this profile:
- `unsigned_bundle`
- `not_anchored`

Those warnings do not invalidate the bundle. They only indicate that signature
and external blockchain anchor are not active in the minimum profile.
